# VetClinic - база даних ветеринарної клініки

Навчальна робота з PostgreSQL та C# (.NET 8). Мета - створити реляційну базу для обліку тварин і прийомів та показати роботу з кількома пов'язаними сутностями через Repository + Unit of Work.

## Що є в системі

База даних складається з 18 таблиць:

- Користувачі та лікарі: `roles`, `users`, `specializations`, `veterinarians`, `veterinarian_specializations`.
- Власники та тварини: `owners`, `pets`, `species`, `breeds`.
- Прийоми й лікування: `appointments`, `medical_records`, `medications`, `prescriptions`, `vaccinations`.
- Послуги й оплата: `services`, `appointment_services`, `invoices`, `payments`.

Зв'язки забезпечуються первинними й зовнішніми ключами. Є зв'язки 1:N, 1:1 та M:N, зокрема зв'язок між лікарями та спеціалізаціями через `veterinarian_specializations`.

У консольній програмі можна переглядати власників, тварин, розклад, прострочені вакцинації та рахунки; реєструвати власника й тварину, додавати нові види та породи; записувати і скасовувати прийоми; логічно видаляти тварину; приймати оплату вже наявного рахунку; перевіряти відкат транзакції. Користувач обирає записи зі списків, а не вводить їхні внутрішні ID.

## Soft Delete та аудит

Soft Delete використовується в `owners`, `pets`, `veterinarians`. Замість фізичного видалення процедури `sp_soft_delete_owner`, `sp_soft_delete_pet`, `sp_soft_delete_veterinarian` встановлюють `is_deleted`, `deleted_at`, `deleted_by`. Історичні записи залишаються. Наприклад, перед видаленням тварини перевіряється, чи немає активних або запланованих прийомів.

У таблицях `users`, `owners`, `pets`, `veterinarians`, `appointments`, `medical_records`, `invoices` зберігаються `updated_at` та `updated_by`. Тригери викликають функцію `fn_set_audit_fields()`, а ID поточного користувача передається через `vet.user_id` в транзакції. У програмі для демонстрації використано тестового користувача №1, без повноцінної авторизації.

## Серверна логіка та індекси

Операції виконуються через функції та процедури PostgreSQL (`fn_create_owner`, `fn_register_pet`, `fn_schedule_appointment`, `sp_cancel_appointment`, `sp_soft_delete_pet`, `fn_register_payment`, `fn_create_species`, `fn_create_breed` та інші). Читання з C# організовано через Views (`v_active_owners`, `v_active_pets`, `v_doctor_schedule`, `v_overdue_vaccinations`, `v_invoices_overview`, каталоги видів, порід і лікарів).

Створені індекси B-tree для звичайного пошуку, GIN з `pg_trgm` для текстового пошуку та GiST-обмеження для недопущення перетину прийомів одного лікаря. Скасування запланованого прийому змінює його статус і звільняє час.

Облік ліків спрощений: таблиця `medications` зберігає ціни та поточні залишки. Автоматичного списання зі складу немає. Програма може приймати платежі за вже створеними рахунками, але не містить сценарію формування нових рахунків через меню.

## Repository + Unit of Work

У `Repositories` є репозиторії власників, тварин, прийомів, довідників і платежів. Вони використовують тільки Views та серверні функції/процедури для роботи з предметними даними.

`Data/UnitOfWork.cs` надає одне підключення та спільну транзакцію для пов'язаних операцій. Під час реєстрації можна однією транзакцією додати вид, породу, власника і тварину. Якщо одна операція завершується помилкою, виконується `Rollback`, а не часткове збереження. Пункт меню «Перевірити Rollback» спеціально демонструє відкат створеного власника після спроби додати тварину з неіснуючою породою.

## SQL-файли та порядок запуску

| Файл | Навіщо потрібен | Виконувати під час встановлення? |
|---|---|---|
| `01_schema.sql` | Створення 18 таблиць, ENUM, базових індексів | Так, лише на порожній БД |
| `02_seed.sql` | Навчальні тестові дані | Так, один раз |
| `03_functions_procedures.sql` | Soft Delete, аудит, функції, тригери, Views, GiST | Так |
| `04_smoke_tests.sql` | Перевірочні SELECT та тестова транзакція | Необов'язково |
| `05_app_support.sql` | View активних власників | Так |
| `06_app_extensions.sql` | Контекст користувача, оплата, скасування прийому та View рахунків | Так |
| `07_catalogs.sql` | Views довідників і функції додавання виду/породи | Так |

**Отже, з 7 файлів 6 є складовими встановлення, а четвертий — необов'язковий файл перевірки.** Задля зрозумілості вони залишені окремими. За бажанням `04_smoke_tests.sql` можна перемістити до папки `Tests`, але він корисний для лабораторної роботи.

Важливо: `01_schema.sql` починається з `DROP TABLE` і **видаляє старі дані**. На вже наявній базі, де виконано файли 01–05, потрібно виконати тільки `06_app_extensions.sql` і `07_catalogs.sql`. Якщо вони вже виконувалися, оновлений `06_app_extensions.sql` можна запустити ще раз для додавання `sp_cancel_appointment`. **Не запускати повторно 01–02 на робочій БД.**

## Запуск C#

Вимоги: PostgreSQL 14+, pgAdmin 4 (не обов'язково для роботи програми), .NET 8 SDK. Залежність `Npgsql` визначена в `VetClinic.csproj`.

1. Створити окрему порожню БД `vet_clinic` та виконати установчі SQL-файли в порядку з таблиці (крім необов'язкового 04).
2. Відкрити `VetClinic.sln` у Visual Studio 2022.
3. У PowerShell у каталозі з `VetClinic.csproj` виконати:

```powershell
$env:VETCLINIC_CONNECTION = "Host=localhost;Port=5432;Database=vet_clinic;Username=postgres;Password=ВАШ_ПАРОЛЬ"
dotnet restore
dotnet build
dotnet run
```

Параметри підключення потрібно замінити власними. Справжній пароль не записувати в репозиторій і не розміщувати на скриншотах.

## Перевірка

Спочатку перевірити списки власників, тварин і розклад. Потім зареєструвати нового власника й тварину, створити новий вид/породу, записати тварину до лікаря, скасувати прийом і перевірити Soft Delete. Пункт Rollback має повідомити, що після помилки тимчасового власника в базі немає. Оплату перевіряти на тестових рахунках: рахунки не генеруються автоматично під час запису на прийом.

Для фінального підтвердження коректності потрібні `dotnet build`, `dotnet run` зі справжнім Npgsql та перевірка запитів у підключеній PostgreSQL.
